## Session 1: realign the project version with the shipped tag (1.8.1)

**Status:** Follow-up to the branch cleanup after #286 landed. Investigation
first, because the reported symptom turned out to have a false premise.

The checked-in `MARKETING_VERSION` read `1.7.2` while the newest tag was
`v1.8.0` — the project file appeared to be *behind* a shipped release. The
obvious reading was a mis-cut tag. It was not.

### What the release path actually does

`v1.8.0` points at `a754160`, where the pbxproj still said `1.7.1`. That is
intentional. `.github/workflows/_build-signed.yml:168` documents it:

> Version is injected explicitly (not read from the pbxproj) so both channels
> get exactly the `CFBundleShortVersionString` + `CFBundleVersion` the caller
> computed. This also removes stable's hidden dependency on a pre-tag pbxproj
> bump: the tag alone now determines the shipped version.

- **Stable** — `release.yml` derives the version from the pushed tag via
  `scripts/validate-release-tag.sh`, then passes it to `_build-signed.yml`,
  which overrides `MARKETING_VERSION` on the `xcodebuild` command line.
- **Nightly** — `nightly.yml` derives from `git describe --tags`, not the
  pbxproj.

So **nothing in CI reads `MARKETING_VERSION` from the project file.** The
shipped 1.8.0 binary reports 1.8.0. The tag is correct.

### Why the tag was left alone

Beyond being correct, `v1.8.0` is load-bearing: it carries a published GitHub
release with three assets marked Latest, and both the Sparkle appcast and the
Homebrew formula resolve download URLs under that tag. Retagging or deleting it
would break in-place updates and `brew upgrade` for existing installs.

### What was done

- [x] Bumped `MARKETING_VERSION` `1.7.2` → `1.8.1` at all four sites
      (two targets × Debug/Release)
- [x] Left `CURRENT_PROJECT_VERSION = "$(MARKETING_VERSION)"` untouched — it
      interpolates, so the four sites are the whole change
- [x] Left every tag and release untouched

### Key decisions

| Decision | Rationale |
|---|---|
| Bump to `1.8.1`, not `1.7.3` | `1.7.2` was itself the drift — it was set after `v1.8.0` had already shipped. Next patch above the real shipped version is `1.8.1` |
| Do not retag `v1.8.0` | The tag is correct by design, and it is referenced by a published release, the Sparkle appcast, and the Homebrew formula |
| pbxproj value is dev-only metadata | It now affects only local Xcode builds; treat the tag as the release source of truth |

- Site count asserted at exactly 4 before the substitution; the edit aborts otherwise
- Diff is 4 insertions / 4 deletions, one file, no other keys touched
- Tests/builds intentionally **not** run locally — PR CI is the gate

## Session 3: `meterbar serve` — token-gated read-only HTTP endpoint (#289)

**Status:** Merged as `c0619a8`. Closes #272. Repair commit `55e1fae`.

A local HTTP view of the same cached usage/cost data the CLI already emits.
Never triggers a provider refresh, never mutates state.

### System flow

```text
meterbar serve ─→ Serve.validate()      ← rejects a blank --token
                     │
                     ▼
              ServeCLI.run()            ← refuses to bind on an unusable token
                     │
                     ▼
         ServeHTTPServer.runAcceptLoop()
                     │  accept() ──→ transient errno? ─→ continue (backoff on EMFILE)
                     ▼
              readRequest(deadline:)    ← wall-clock bound, not SO_RCVTIMEO
                     │
                     ▼
              ServeRateLimiter ─→ 429
                     │
                     ▼
              ServeRouter.handle()      ← auth BEFORE routing
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
   GET /usage                GET /cost
        └──── SharedDataStore / CostSummaryStore (cache only, no refresh)
```

### CodeRabbit repair loop

CI was green on the first head; `required_conversation_resolution` held the PR
at `BLOCKED` on five unresolved threads. All five were verified against source
before any fix was written.

| Severity | Defect | Fix |
|---|---|---|
| Major (security) | An empty configured token compared equal to the empty string a caller gets from a bare `Authorization: Bearer ` header — the auth check authorized everyone. Reachable via `--token ""`, since `token ?? generate()` only substitutes for `nil` | Three layers: `Serve.validate()` rejects a blank flag, `ServeCLI.run` refuses to bind, `ServeToken.matches` fails closed |
| Major | `guard clientFD >= 0 else { return }` killed the whole listener on a transient `accept` failure | `isTransientAcceptError` + `continue`; EMFILE/ENFILE back off 100ms rather than spinning |
| Major | `SO_RCVTIMEO` bounds each `recv`, not the connection — it restarts on every byte, so a slow-loris client could hold a handler thread open indefinitely | Socket option drops to a 1s poll; `readRequest` takes a wall-clock `deadline` re-checked each iteration |
| Major | `(try? document.jsonData()) ?? Data()` returned an empty body wearing `200 OK` / `application/json` | `jsonResponse` returns a real 500; `errorResponse` falls back to a JSON literal, never empty `Data` |
| Minor | MD040 — unlabeled code fence in the schema doc | Fence tagged `text` |

### Key decisions

| Decision | Rationale |
|---|---|
| `requestTimeout` on `Configuration` with a 5s default | Exists only so the slow-loris test can drive it to 1s and stay fast. The CLI surface deliberately does not expose it |
| `ServeRouter.jsonResponse` widened `private` → `internal` | `@testable import` needs it to drive the encode-failure path via a `FailingDocument` |
| Blank-token rejection at three layers, not one | Validation is the usable error, the bind refusal is the guarantee, and `matches` failing closed is what keeps a future missed check from reopening the endpoint |
| Auth checked before routing | An unauthenticated caller cannot use status codes to enumerate which paths exist or which methods they take |

### Mistakes and fixes

| Mistake | Fix |
|---|---|
| `XCTAssertNotNil(JSONSerialization.jsonObject(...))` without `try` — compile error | Added `try`; the enclosing test already `throws` |
| `swift test` locally showed 18 failures in `SessionWakeController` / `UsageDataManager` / `WakeQuotaProviderSelection` | Not a regression. Reproduced identically with the changes stashed, and CI's `Tests + coverage gate` is green on the same commit — a local machine-state dependency in those suites |
| The Xcode-built `MeterBar.app` shipped a `Contents/Helpers/meterbar` with no `serve` subcommand | The CLI is injected *after* `xcodebuild`, by `scripts/build-universal-cli.sh` (`_build-signed.yml:193`). Ran it explicitly against the built bundle |

## Session 5: Grok reads "Failed to parse response" on a brand-new billing cycle

**Status:** Done. Branch `claude/grok-offline-logo-0e8f46`, worktree
`.claude/worktrees/grok-offline-logo-0e8f46`.

Reported as "Grok is offline" — orange sidebar dot, Overview `Status: Refresh
failed` / `Updated: No data`, Extra Usage `Unknown`. It was never offline: the
Grok Build pane said `Connection: ✓ Connected` in the same screenshot, which is
the tell. Handshake fine, mapping broken.

### Root cause

`initialize` (id 1) and `authenticate` (id 2) both succeed. The `_x.ai/billing`
reply (id 3), captured live against `grok --no-auto-update agent --no-leader
stdio` on CLI 0.2.112, is:

```json
{"jsonrpc":"2.0","id":3,"result":{"config":{
  "currentPeriod":{"type":"USAGE_PERIOD_TYPE_WEEKLY",
                   "start":"2026-07-22T15:05:27.877598+00:00",
                   "end":"2026-07-29T15:05:27.877598+00:00"},
  "onDemandCap":{"val":0},"onDemandUsed":{"val":0},"prepaidBalance":{"val":0},
  "isUnifiedBillingUser":true,
  "billingPeriodStart":"2026-07-22T15:05:27.877598+00:00",
  "billingPeriodEnd":"2026-07-29T15:05:27.877598+00:00"},
  "subscription_tier":"X Premium"}}
```

No `creditUsagePercent`, no `usagePeriods`. Both limits came out `nil`, the
`guard` in `map` threw `.invalidResponse`, and `serviceError(from:)` turned that
into `.parsingError` — "Failed to parse response", plus a parse-health drift
count.

**The payload is a JSON projection of protobuf, and proto3 omits scalar
defaults.** `creditUsagePercent` is missing from a fresh cycle *precisely
because* it is `0.0`. `strings` on
`~/.grok/downloads/grok-0.2.112-macos-aarch64` confirms it is still a member of
the same `struct BillingConfig` — omission, not a rename. The monetary fields
survive as `{"val": 0}` only because they are submessages, not scalars. That
asymmetry is the whole bug.

CodexBar (`steipete/CodexBar`, checked per the ask) reached the same reading:
a current billing period with an omitted `credit_usage_percent` is zero usage.

### What was done

- [x] Percent resolution order, most-trusted first: a listed weekly period's
      `usagePercent` → reported `creditUsagePercent` → `derivedCreditPercent`
      (`totalUsed / monthlyLimit * 100`) → proto3's implied `0`
- [x] `impliedZeroPercent(for:)` gated twice: a dated cycle window **and**
      either a named `config` container or at least one decoded billing field
- [x] `GrokBillingConfig.Credits` (own object or inlined) feeding
      `monthlyLimit` / `totalUsed` / `includedUsed`
- [x] `GrokBillingResult.hasBillingConfigContainer` — the provider naming the
      container is it stating this *is* a billing config
- [x] Official Grok mark shipped: `MeterBar/Resources/ProviderIcon-grok.svg`
      plus `ProviderLogoKind.grok.resourceName`, replacing the `bolt.fill`
      SF Symbol fallback
- [x] Widget: `MeterBarWidget/Assets.xcassets/GrokIcon.imageset` at 1x/2x/3x,
      and `.grok` dropped from `WidgetProviderIcon`'s SF-Symbol branch
- [x] 6 tests written before the fix (TDD), including a full ACP transcript
      replay of the verbatim 0.2.112 payload

### Key decisions

| Decision | Rationale |
|---|---|
| Derived credit percent is tried *before* the implied zero | A credits account with real spend and no reported percent would otherwise under-report as 0% — the same fabricated reading, one layer down |
| The implied zero keys off `config.fallbackPeriod`, never a `usagePeriods` window | A period the provider listed and left without a percent is a *per-period* omission, not this account-wide default. Keeps `testUsageWithoutAnyReadablePercentIsUnknownRatherThanZero` honest |

| Grok's SVG uses `viewBox="-3 -3 30 30"` | The mark's own coordinate space fills its box edge to edge; the other logos are ~10..90 within `0 0 100 100`. The inset viewBox matches their optical weight |

## Session 6: per-profile Claude credential resolution (#292 phase 1)

**Status:** Implemented on `claude/account-sync-genfeed-shipshitdev-356985`.
Phase 1 of epic #292 only — per-account auth state, delegated refresh, and
Keychain-prompt hygiene are phases 2–4 and are deliberately not in this change.

### The bug this closes

Every Claude account shared one credential lookup: the single Keychain item
`Claude Code-credentials`. That item belongs to whichever identity last logged
in through the unscoped `~/.claude` profile. The previous code dodged the
resulting cross-contamination by refusing OAuth outright for any scoped
profile — `ClaudeCodeLocalService.prefersOAuth` returned `false` unless the
account was the unscoped default — and forcing those accounts onto `claude
/usage`. But that CLI no longer renders `/usage` in a headless spawn, so a
scoped profile had no working usage source at all.

### What Claude Code actually writes

Per profile, the Keychain service is:

```
Claude Code-credentials-<first 8 lowercase hex of sha256(configDirPath)>
```

no trailing newline. Reproducible with:

```bash
printf '%s' /Users/you/.claude-work | shasum -a 256 | cut -c1-8
```

`~/.claude` is the exception: it has **both** the bare item and its suffixed
(`162468c0`) form. Scoped profiles only ever get the suffixed one. A
`<configDir>/.credentials.json` file (mode `0600`) is the non-Keychain fallback.

### What was done

- [x] New `ClaudeCredentialResolver` — pure derivation of the effective config
      directory, the per-profile Keychain service name (CryptoKit SHA-256, as
      already used in `WakeSession.swift` and `ApiUsageStore.swift`), and the
      ordered candidate list
- [x] New `ClaudeCredentialStore` — the thin I/O shell that walks those
      candidates, injectable for tests
- [x] Extracted `ClaudeCodeAccount.expandConfigDirectory` so the resolver and
      the CLI's `CLAUDE_CONFIG_DIR` agree on one resolved path
- [x] `ClaudeCodeLocalService` credential accessors are now account-scoped;
      `prefersOAuth` deleted
- [x] OAuth publishes to provider-wide `@Published` state only for the default
      account, mirroring what the CLI path already did
- [x] `LiveWakeQuotaProvider` threads the account through its OAuth closure
- [x] 12 new resolver tests; obsolete `prefersOAuth` tests rewritten against the
      resolver rather than deleted

### Candidate order, and why

1. `Claude Code-credentials-<sha8>` — the profile's own item
2. `Claude Code-credentials` — **only** when the resolved directory is
   `<realHome>/.claude`
3. `<configDir>/.credentials.json`

Keychain before file because it is authoritative on macOS. Empty payloads count
as misses, so a stale emptied Keychain item cannot shadow a good file.

### Key decisions

| Decision | Rationale |
|---|---|
| Delete `prefersOAuth` rather than gut it | With per-account resolution the pure policy question collapses to the `oauthEnabled` opt-out. Applicability is now decided by whether a credential resolves — that is I/O, and belongs in the store |
| Re-enable OAuth for *every* profile | The anti-contamination guarantee moved from a policy refusal into `candidates(for:)`: a scoped profile structurally cannot reach the bare item |
| Gate OAuth `@Published` writes on `publishesSharedConnectionState` | Custom accounts can now succeed *and* fail via OAuth; without the gate a secondary profile's error would clobber the provider-wide card |
| Expand `~` in one shared helper | A raw `~/.claude-work` handed to node as `CLAUDE_CONFIG_DIR` resolves against cwd, so hashing the raw string would never match a real item |

## Session 7: per-account auth/staleness state (#292 phase 2)

### Problem

Phase 1 gave each account its own credential, but the UI still had a single
shared notion of "connected". A logged-out secondary profile therefore rendered
a green **Healthy** band built from its last successful reading — the exact
failure the epic names in its acceptance criteria.

Three independent links produced that outcome, and all three had to be cut:

1. `ClaudeCodeLocalService` computed a per-account auth/error state, then
   discarded it for every non-default account because every `@Published` write
   was gated on `publishesSharedConnectionState`.
2. `UsageDataManager.fetchClaudeCodeAccountMetrics()` substituted the previous
   cache on a failed leg and recorded nothing about the substitution, so the
   card could not tell a fresh reading from a month-old one.
3. `ProviderCardPresentation.statusText` derived its word purely from
   `QuotaBand`, which only ever sees percentages.

### Change

- **`ClaudeCodeAuthState`** gains `.stale(since:)`, plus a new
  `accountAuthStates: [UUID: ClaudeCodeAuthState]` published on the service.
  The per-account writes are deliberately ungated; only the provider-wide
  `authState`/`hasAccess`/`lastError` writes stay behind
  `publishesSharedConnectionState`.
- **`fetchUsageViaCLI(account:isLoggedOut:)`** — when OAuth returned "no
  credential", a CLI leg that then fails to parse means logged out, not
  malformed. Without this thread the acceptance case surfaced "Needs attention"
  instead of "Login required".
- **`ClaudeAccountStateResolver`** (new) — the pure rule that turns
  `(serviceState, didSucceed, failure, cachedLastUpdated)` into the state a card
  should show. `needsLogin`/`unavailable` outrank staleness, because "your data
  is old" would hide the reason refreshing keeps failing.
- **`ProviderAuthNotice`** (new) — the card-level overlay. `QuotaBand` stays a
  pure function of the percentages; the notice sits on top of it and wins
  wherever the card prints a status word or colour, including
  `accessibilityLabel`.
- **`UsageDataManager`** resolves and publishes `claudeCodeAccountStates` once
  per refresh cycle, in account-store order, alongside the cache substitution
  it already performed.

### Key decisions

| Decision | Rationale |
|---|---|
| Overlay instead of a new band case | `QuotaBand` is shared with the widget and is genuinely percentage-only. A stale card's 12% really is healthy — the problem is the missing "…as of three days ago", which is not a band's job |
| `needsLogin` outranks `stale` | Both are true for a logged-out account, but only one tells the user what to do about it |
| `authNotice` declared `var` | A defaulted `let` is dropped from the memberwise initializer entirely, which would leave the builder unable to set it; the implicit `nil` keeps ~7 existing direct constructions compiling untouched |
| Extra-usage probe left alone | Its scoped resolution is already satisfied by phase 1's `getCredentials(for: account)` — reimplementing it here would be churn |
